requirements 1-8 only (`manager/supervisor.py`, `tests/manager/**` except fixtures, this file); requirement 9

or probed here — no production state, credentials, service, VM restart or network access was used.

## What changed

`Supervisor.persist` and `Supervisor.sync_repo_before` no longer use `git merge` to reconcile a diverged clone.
Both now share one routine, `_fetch_and_rebase_onto_remote`: it first checks `.git/rebase-merge` and
`.git/rebase-apply` (a leftover in-progress rebase blocks immediately, before any git call); then runs `git fetch
-q origin`; then, only when `origin/<branch>` is not already an ancestor of `HEAD`, runs `git rebase -q
origin/<branch>`. A failed fetch is recorded as a `pending` failure (step `fetch`); a failed rebase runs `git
rebase --abort`, checks its result, and records a `blocked` failure (step `rebase`) with either the rebase's own
output or, when the abort itself fails too, both outputs joined `<rebase output> | abort: <abort output>`. No
push is ever attempted after a fetch or rebase failure, and no `--force`, `reset` or `checkout` is ever issued. A
clone with no unpushed commits simply fast-forwards through the rebase; a clone with an unpushed commit gets it
replayed onto the remote's new tip, producing a linear history with both the remote's and the local commit's
content present, pushed as a plain `git push origin HEAD`. `persist` calls this routine once, right after staging
and committing and immediately before the push, on every attempt (first or retry) — so a push is always preceded
by a fresh look at the remote. `sync_repo_before` calls it once at the start of every turn, after its own dirty
check, and — unlike a tick — retries even a `blocked` status, since that is the turn-start repair path for a
previously blocked episode. When `sync_repo_before` blocks (dirty tree, in-progress rebase, or a rebase conflict),
the following `persist` in the same turn or tick now short-circuits with zero git calls and the originally
recorded step/error untouched, instead of overwriting it with a fresh `dirty` failure as before.

Every persistence failure (`_persistence_fail`) now also carries `since` (the clock at the episode's *first*
failure, kept across every later failure of the same episode and across a restart), `failures` (a count), and
`notice_at` (`null` until a notice is actually queued). A fresh episode (the first failure after `synced` or
absent) gets a new `episode_id` and `notice_at: null`; a failure while already `pending`/`blocked` keeps all
three and only bumps `failures`. No notice is queued at the moment of failure any more — that was today's
"persistence pending (episode ...)" post, which leaked the raw git stderr including the `hint:` block and the
episode uuid. Instead, `_maybe_queue_persistence_notice` is checked on every tick (`reconcile_persistence`, which
`run_once` runs every tick regardless of status) and after every failed attempt: once `clock_epoch() - since >=
PERSISTENCE_NOTICE_AFTER_S` (300) and `notice_at` is still `null`, it queues one top-level, dev-channel,
no-thread line through the existing stable-id outbox dedup (`persistence-<episode_id>-notice`) and stamps
`notice_at`. The check never touches git, so it fires on a tick before the 60-second retry deadline, and on a
`blocked` episode that ticks never retry. The text is built by the new module-level `notice_error_summary(text)`:
it splits the stored `<step>: <detail>`, picks the first `error:`/`fatal:` line of the detail (that prefix
stripped) or else the first non-`hint:` line or else `"unknown error"`, drops an inline `hint:` and everything
after it, collapses whitespace, redacts any `scheme://user[:pass]@host` to `scheme://<redacted>@host`, and cuts
the result to 200 characters — so the notice is one line with no stderr, no hint block, no episode uuid. A
successful push (`_persistence_recovered`) clears `since`/`failures`/`notice_at` along with the existing fields,
and queues a `persistence recovered: synced at <sha12> after <M> min` line only when the episode being closed had
`notice_at` set (a quiet recovery inside the five minutes posts nothing, matching the merged outcome).

A b7-era `pending`/`blocked` record with no `since` field is adopted, never rejected or crashed on
(`_adopt_legacy_persistence`, called by both `reconcile_persistence` and `_persistence_fail`): `since`/`failures`
start as if this were the first observed failure (`failures` 1, or 2 when the observation is itself a failure),
`episode_id`/`error` are kept, and `notice_at` is set to the adoption clock only when the legacy
`persistence-<episode_id>-failed` notice is already queued in the outbox or already has a delivered receipt — so
an episode whose old-style notice already went out never gets a second one and still posts exactly one recovered
line, while one that never got a notice follows the new five-minute rule from the moment it is observed.
`PERSISTENCE_NOTICE_AFTER_S = 300` is a new module constant; `PERSISTENCE_RETRY_AFTER_S` (60) and every other rule
of b7 requirement 19 (every git return code checked, no automatic conflict resolution, the dirty-tree block, the
60-second deadline never reset by a new turn, `no_repo`) are unchanged.
