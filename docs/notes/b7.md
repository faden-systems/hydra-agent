# waiting visibility, bounded continuation and persistence repair

PR #40 off `acf80e9`). Candidate HEAD at the time of this note: `aa1907378c885ec98aab61c3153804ee4e69416e`.

## Problem

The bridge twice stopped receiving while its TCP socket stayed `ESTABLISHED` — there was no liveness check other
than the dead socket itself, and no bounded, visible recovery path. Aggregate Claude `input_tokens` (summed across
every request in a turn, including large tool-result replays) was mistaken for carried context, triggering
compaction on ordinary multi-step turns that had not actually grown the session. Track `stage` text accumulated
full history forever, flooding `hydra status` and every turn's prompt. Empty Slack replies, blocks-only messages
(no top-level `text`), and a `hydra post` read race (outbox file deleted between the existence check and `open()`)
obscured operator reports. Issue #37 added: hidden Claude error text swallowed by naive JSON parsing, an engine
"quota" classifier that matched substrings like `rate` inside `generate`/`separate`, failed compaction attempts
polluting the shared memory ledger as if they were real turns, a compaction mechanism (`/compact`) that assumed
success without checking anything, and Slack messages carrying an unparsed `*Sent using* <@ID>` attribution footer
that broke command parsing. The founder's 2026-10-03 amendment (PR #40) added: the manager had no way to signal
"I'm done, nothing to do but wait" or "I can keep going" without an operator or a Slack-text heuristic, no visible
waiting indicator, no bounded automatic continuation, and `persist()` could silently claim a commit was "pushed"
when the push itself had failed, or silently stage/commit files outside its own ownership.

## Implementation

**1-2. Bridge liveness and reconnect** (`manager/bridge.py`): `SocketHealth(client, clock=time.monotonic,
timeout_s=300)` tracks the monotonic time of the last Socket Mode envelope (`note_envelope`, installed as a raw
`socket_mode_request_listener` — fires before Bolt's own event-type filtering) and the last *changed*
`client.current_session.last_ping_pong_time`; `check()` is unhealthy when `is_connected()` is false or neither has
been seen within `timeout_s`. A session replacement that happens to carry the same stale pong value cannot buy
fresh activity — only a changed value counts. `run_socket_mode(handler, stop, clock=, poll_s=10,
reconnect_timeout_s=30)` disables the SDK's own `auto_reconnect_enabled`/`default_auto_reconnect_enabled`,
connects once, installs the listener, then polls `SocketHealth` in the *calling* thread (never a background one,
so a failed recovery's exception actually kills the process instead of a thread nobody is watching); a stuck
`connect_to_new_endpoint()` is bounded by running it in a daemon thread and joining with a timeout. `serve()` now
calls this instead of `SocketModeHandler(...).start()` (which blocks forever and offers no way back out); its
`finally` stops the outbox pump and closes the client. `main()` turns either a raised exception or a nonzero
`SystemExit` into a nonzero process exit.

**3-4. Context tokens vs aggregate** (`manager/supervisor.py`): Claude now runs with `--output-format stream-json
--verbose` (never `--include-partial-messages`). `_parse_claude_output` parses every complete JSONL record (or a
single terminal JSON object for the old `--output-format json` shape, or a legacy plain `[usage] key=value`
line), takes `context_tokens` from the *first* `type: assistant` record's `usage` (`input_tokens +
cache_creation_input_tokens + cache_read_input_tokens`, each counted once — nested `cache_creation` breakdowns are
never re-added), and keeps the terminal record's aggregate `tokens`/`input_tokens` for accounting only. A missing
or invalid first-request usage (bool/negative/non-finite) leaves `context_tokens` unknown rather than falling back
to the aggregate. `schedule_compaction`, `verify_compaction`, and the new `last_claude_context_tokens()` (replacing
the old aggregate lookup) all use `context_tokens`; `turns.jsonl` records it alongside the legacy `input_tokens`;
`hydra usage` prints `context_tokens=<N|unknown>`.

**5. Track `now`/history** (`manager/supervisor.py`, `manager/hydra`): every track gets a `now` (<=240 chars, one
line); `tracks_summary`/`status_text` show `now` first, one line per track, and `migrate_track_history(home,
repo)` is the one-time mechanical migration: validates every track id against `[A-Za-z0-9_-]+` *before* writing
anything, archives the complete legacy `stage` text to `factory/log/tracks/<id>.md` (appending, never duplicating
or deleting existing content), derives a conservative `now` from the archived text's last nonblank line when none
was already valid, and atomically replaces `state.json` with `os.replace` only after the archive write — a crash
between the two is idempotent on retry. No repo configured is a byte-for-byte no-op. `hydra migrate-tracks` runs
it from the CLI; the supervisor runs it itself before building the prompt and again before `persist()`, so both a
stale on-disk `state.json` and whatever the engine wrote mid-turn get migrated the same way.

**6. No empty replies** (`manager/supervisor.py`): `plan_deliveries` decides per Slack thread, not globally across
a mixed batch: a blank reply for a thread touched only by indirect/informational events is skipped (logged `turn
N: no reply text, delivery skipped`); a thread touched by an `instructs:true` sender or a mention gets
`NO_REPLY_PLACEHOLDER` (`"(turn produced no reply text)"`, logged `..., placeholder sent`). `deliver()` also
refuses to post a legacy blank item recovered from `inbox/pending-replies.jsonl`. CLI reply-file semantics and
handoff parsing are unchanged.

**7. Slack block normalization** (`manager/bridge.py`): `normalize_blocks(blocks)` recursively renders
`rich_text` (sections, lists — each item itself a section — quotes and preformatted code, whose own `elements`
are leaves directly), `section`/`context` plain or mrkdwn text, user mentions, links (label else url), and emoji;
malformed or unknown elements (including a bare `None`) are ignored, never raised. `Bridge.handle_message` uses it
only as a fallback when the top-level `text` is blank — nonblank text is authoritative, never duplicated — and the
same normalized string feeds the mirror, mention detection, assignment detection and the queued payload.

**8. Outbox race and receipts** (`manager/supervisor.py`): `read_jsonl` now tolerates the file disappearing
between the existence check and `open()`. `post_receipt(home, id)` / a durable `inbox/outbox-receipts.jsonl`
record posted/failed per id, written under the existing outbox lock *before* the queued entry is removed (`
_write_outbox`, kept as the crash-injection seam); `drain_outbox` recognizes an existing receipt for an item still
queued after an interruption and removes it without reposting. `hydra post` now waits on `post_receipt` instead of
inferring success from the queue's absence.

**9-10. Tests and these notes.** See Validation and Changed assertions below.

**11-12. Classification and model fallback** (`manager/supervisor.py`): `invoke()` parses stdout on every return
code; a nonzero rc is a failure even when the JSON looks successful, and a failed/`is_error` result never saves a
session id. `classify_engine_error(text)` matches phrases (`\bcredits?\b`, `\busage limit\b`, explicit
`http`/`status` + `401`/`403` or the words unauthorized/forbidden, `\brate[\s-]?limit\b`/`\b429\b`, `prompt
(is )?too long`), not substrings — `generate`/`separate` never match `rate`. `run_engines` tries each account's
current model, and on a `credits`/`usage_limit` failure, each distinct configured `engine_fallback.claude_models`
model (excluding Fable and the current model) once on the *same* account before the next account; `auth` skips
that retry; `prompt_too_long` skips the rest of the Claude family outright (a different account cannot fix a
session-level prompt-length problem). Every attempt (success or failure) is recorded in `logs/attempts.jsonl`;
`successful_ledger()` filters `kind=attempt`, `success=false`, error-bearing and failed-compaction rows out of
`switch_for`/`family_last_at`/`memory_preamble`/the transition window, without ever rewriting the historical
ledger file. `engine-runtime.json` separates the operator's `configured` pair (touched only by an explicit
`set_engine(..., explicit=True)`, the bridge/CLI `engine` command) from the currently `effective` one; a
credits/usage/auth-driven switch away from `configured` opens one fallback episode (a stable `episode_id`, `since`,
`reason`), announced once via the durable outbox (never a direct Slack call) with the words `fallback started`;
returning to `configured` — even via a fresh explicit selection that happens to match the already-effective pair —
closes it with one `fallback ended` notice. `persistence_checkpoint(name)` is called right after each durable step
(`fallback_start_saved`/`_queued`, `fallback_end_saved`/`_queued`); a pending-notice flag survives a crash at any
point and is reconciled, deduplicated against an existing receipt, before the next `run_engines`.

**13. Rollover instead of `/compact`** (`manager/supervisor.py`): `run_compaction` now runs the `[compaction]`
memory-writing turn on the existing session; only once it exits 0, produces all five required handoff lines, and
the before/after SHA-256 of `MEMORY.md` actually differ, does it generate a new UUID and call
`replace_session_id(new_id)` (`os.replace`, raising without touching the old id on failure). `rollover-intent.json`
(old id, new id, `started: false`) is written and `persistence_checkpoint("rollover_intent_saved")` called before
the replace; `"rollover_id_replaced"` after it; `"rollover_state_saved"` after `compaction_state()['last']` and the
ledger/turns records are written. A crash at any of the three checkpoints is reconciled, once, the next time a
Supervisor is constructed — never a second memory turn, and the new id is never `--resume`d before a successful
invocation has actually started it (`started: true`). A plain write failure (caught `OSError`) durably cancels the
intent and keeps the old id. `compaction_state()['last']` records both ids with `ok: null` immediately; a later
measured turn alone may set `ok: true` using the existing threshold — an unmeasured turn leaves it pending rather
than claiming success or failure. `config.json`'s `compaction.rollover_enabled` defaults `false`: automatic
rollover stays held (`compaction_state()['last'].error` contains "held") until the founder lifts that hold; the
Supervisor never touches the session id or runs a memory turn while held. Offline fixtures and tests explicitly
set it `true`.

**14. Attribution footer** (`manager/bridge.py`): after block normalization and before command parsing,
`strip_attribution_footer` removes one trailing `*Sent using* <@ID>`/`*Sent using* <@ID|label>`, separated by a
newline or spaces, that ends the message; a footer on a `>`-quoted line or inside an (optionally unclosed)
triple-backtick fence is left alone, as is anything that is not exactly trailing. The routing copy (mention
detection, command parsing, the queued payload) uses the cleaned text; the mirror may keep the raw one. Sender
authorization is unchanged — based on platform metadata (`user`/`bot_id`), never anything in the footer.

**16. `work-status.json` and `settle_work`** (`manager/supervisor.py`, `manager/CLAUDE.md`): the manager-engine
itself writes `$HYDRA_HOME/work-status.json` at the end of a turn (never parsed from Slack text); `turn`, `mode`
(`continue`/`idle`/`waiting`/`done`), `track`, `channel`, `thread_ts`, `message_ts` are always required, plus
`next_action` (continue), `deadline` (idle/waiting), `who`/`since` (waiting). `_validate_work_status` checks types
(no bools-as-numbers), finiteness, a 4096-character string cap, and that `turn` matches the turn just run;
anything short of that logs a diagnostic and disables automatic continuation for that turn without guessing.
`Supervisor.settle_work(n, events)` is called after every successful delivery and persistence *attempt* (persist's
own git outcome does not gate it), including a blank reply; a failed engine turn never calls it. A delivery that
fails is deferred to `inbox/pending-replies.jsonl` (which already carries the original `turn`/`events`); once
`deliver_pending()` recovers it, `settle_work` runs exactly once, using the original events (re-read by id from
the durable event log, not just the ones still "pending").

**17. Bounded automatic continuation**: for `mode: continue`, `_maybe_continue` requires no PAUSE, no
`inbox/pending-replies.jsonl`, and no other event already queued (a manual `continue <track>` the operator queued
counts as exactly such an event, so it suppresses an automatic duplicate for free). A deterministic `continue-<turn>`
id and a reservation (`logs/continuation-reservations.jsonl`, counted within a rolling 3600-second window —
`now - at < 3600`, so a backward clock can never free a slot it hasn't actually earned by elapsed time) are
persisted, `persistence_checkpoint("continuation_reserved")` called, *then* the informational event itself is
appended (`instructs: false`; it carries the authorized track/action, never new authority) and
`persistence_checkpoint("continuation_enqueued")` called. `logs/continuation-intent.json` records the pending
reservation; a restart reconciles an incomplete one once (finishing the enqueue if the event was never created,
or doing nothing if it already was — the dedup is on the deterministic id). `continuation.max_per_hour` (default
6; an invalid value — negative, non-int, bool, `>60` — disables with a logged diagnostic; `0` disables silently
since that is a legitimate "off") is checked at reservation time. `run_once` defers a continuation event behind
any newly-arrived real event in the same batch, so a fresh founder message is never executed after an automatic
task that happened to queue first.

**18. Waiting footer and reaction**: before `plan_deliveries`, `_prepare_waiting_footer` turns a validated
`idle`/`waiting` status into `⏲ next check HH:MM PDT`/`⏲ waiting on <who>; next check HH:MM PDT` (America/Los_Angeles,
`%Z` naturally gives PST outside DST) and appends it to the reply unless that exact footer is already present
(an engine that already wrote a correct one is not duplicated). The reaction target is the event in *this turn's
own batch* whose `channel`/`ts` match the validated `channel`/`message_ts` — never an unverified value taken
directly from the file. `logs/work-reaction.json` persists the desired target/name/action and a `confirmed` flag;
a failed `add`/`remove` is logged and left unconfirmed so `reconcile_work_reaction` (called on every `run_once`
tick, including one with no events, and right after a restart) retries it next tick without ever claiming false
success; switching away from idle/waiting removes a standing clock. `status_text` and the Slack `status` command
show `waiting on <who> since HH:MM PDT` or `idle until HH:MM PDT` using the same conversion; `continue`/`done`
never show one, and a home with no (valid) `work-status.json` keeps the exact legacy output.

**19. Truthful persistence** (`manager/supervisor.py`): `sync_repo_before` now fetches and merges (an ordinary
`git merge`, never `--ff-only`-only, so a genuinely diverged clone reconciles instead of refusing to pull) instead
of `pull --ff-only`; a real conflict aborts the merge and marks `blocked`, retaining local work untouched. Before
touching git at all, both `sync_repo_before` and `persist` refuse (status `blocked`, no staging/committing/
unstaging) when `git status --porcelain -uall` shows anything outside `factory/state.json`, `factory/log/`, or
`factory/manager-memory/`. `persist` checks every git return code; a failed add/commit/push is `pending` (an
unpushed local commit is retried on a later call *even with nothing newly staged*, since the commit already
exists), never reported `synced`; `logs/persistence.json` carries `status`, `last_successful_push_sha`,
`pending_local_sha`, `error`, and a 60-second `retry_after` that a new turn does not reset — `reconcile_persistence`
(called on every `run_once` tick, including one with no events) only retries a `pending` status once its own
deadline has passed, never a tight loop; `blocked` needs the founder, not an automatic retry. One top-level
dev-channel notice per failure episode and one `recovered` notice on the next successful sync are queued through
the same durable, deduplicated outbox helper the engine-fallback episodes use. A missing repo is an explicit
`no_repo` status, distinct from `pending`/`blocked`.

## Rollback

Rollback is the existing `hydra update`-driven "deploy the prior commit" path; nothing here changes it. Specific
to this build: `logs/compaction.json`, `logs/persistence.json`, `logs/attempts.jsonl`,
`logs/continuation-reservations.jsonl`, `engine-runtime.json`, `rollover-intent.json`, and the track archives under
`factory/log/tracks/` are additive and read tolerantly by old code (an unknown key is ignored; `tracks_summary`'s
dict/list handling for a plain string track value, used by pre-b7 state, is unchanged) — a rollback to the prior
manager code continues to read a short `stage` exactly as before, and no archive or compact state is deleted by
rolling back. Because `compaction.rollover_enabled` defaults `false`, a rollback never has to "undo" a live
session-id change this build might have made (it made none; the manual hold was never released during this
build). The outbox and its receipts (`inbox/outbox.jsonl`, `inbox/outbox-receipts.jsonl`) are append/replace files
a prior binary already knows how to read or safely ignore.

## Engine failures

`classify_engine_error` is phrase/token-based specifically so a crash message containing an incidental digit
sequence or a word like `generate`/`separate` is not misread as a rate limit (`rate_limit_matrix`/
`test_engine_fallback.py::test_classification_is_phrase_not_substring`). The historical-ledger filter
(`successful_ledger`, used by `switch_for`/`family_last_at`/`memory_preamble`/the transition window) excludes
`kind: attempt`, `success: false`, any row carrying an `error` key, and a `kind: compaction` row whose
`compaction.ok is false` — but never rewrites `LEDGER.jsonl` itself; an old row with no `success` key at all
(pre-b7 history) is retained as successful, since absence is not the same as `false`. Config keys:
`engine_fallback.claude_models` (default `[claude-sonnet-5]`; `[]` disables the same-account retry step
entirely) and `dev_channel` (where fallback/persistence episode notices land). Notice deduplication uses a
deterministic outbox id (`fallback-<episode_id>-start`/`-end`, `persistence-<episode_id>-failed`/`-recovered`)
checked against both the live outbox and `post_receipt` before enqueueing, so a crash between "durably decided to
notify" and "confirmed queued" — reconciled once at the next Supervisor construction, via the same
`persistence_checkpoint` seam used for the episode transition itself — can never lose or duplicate the notice,
even once a bridge receipt already exists for it. No real account was probed in any test; every fallback/attempt
test in this build patches `Supervisor.invoke` or uses a local recording fixture binary.

## Rollover

`compaction.rollover_enabled` defaults `false`: the founder's manual-recovery hold (today's 51 MB conversation,
the live session id) is a *runtime* decision this spec does not touch, so a held attempt records
`compaction_state()['last'].error` containing `"held"` and performs no engine call and no file write beyond that
diagnostic. Offline tests and fixtures (`tests/manager/test_rollover.py`, the `rollover`/`notice_crashes`/
`continuation_crashes` functions in `loops/b7.acceptance.py`, `test_compaction.py`'s `config()` helper) explicitly
set it `true` to exercise the live code path end to end without ever touching a real account. `rollover-intent.json`
plus the three `persistence_checkpoint` calls (`rollover_intent_saved`/`rollover_id_replaced`/`rollover_state_saved`)
mean a process death at any of the three points recovers the *same* intended UUID on restart — never generates a
second one, never re-runs the memory-writing turn, and never resumes the new id before it has actually been
