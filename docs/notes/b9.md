## Problem

`SocketHealth` already proves a quiet interval was *healthy* (requirement 1, loops/b7.md), but nothing observable
proves it was carried by pongs rather than, say, a monitor that stopped checking: the counters only lived in
private fields, the bridge never wrote a journal entry for a pong, and systemd uptime cannot show an interval was
envelope-free. Idle-pong is the single open b7 item (founder decision 1791142113.617989: blocks-only accepted,
idle-pong deferred).

## Implementation

**1. Counters on `SocketHealth`** (`manager/bridge.py`): `envelope_count` increments once per `note_envelope`
call (the raw receipt listener, before Bolt's own filtering, any arguments); `pong_count` increments once per
*changed* `client.current_session.last_ping_pong_time` observed by `_note_pong_if_changed` — the same method
`check()` already called, so an unchanged value, or a replacement session carrying the same old timestamp, never
counts, and outbound pings/Web API calls (which never touch either seam) stay invisible. Both start at 0 on
`__init__` and never reset while the process (and this `SocketHealth` instance) lives. `counters()` returns
`{"pong_count": ..., "envelope_count": ...}`; both are also plain integer attributes.

**2. `reconnect_count` on `run_socket_mode`**: a local variable, incremented once immediately before each call to
`_reconnect_or_die` (so before that attempt's outcome is known — a fatal attempt is still counted) and never reset
within one invocation; it accumulates across however many recovery attempts happen in that monitor's lifetime.
`SocketHealth`'s own counters are untouched by a recovery, since the same instance survives it.

**3. The observation file**: `run_socket_mode(handler, stop, clock=time.monotonic, poll_s=10,
reconnect_timeout_s=30, observation_path=None)` — a new keyword-only-by-convention, backward-compatible parameter
(every existing b7 call site, which never passes it, is unaffected). `serve()` passes
`os.path.join(home, "logs", "bridge-health.json")`. Each poll iteration's health-check-and-any-recovery runs
inside a `try`, with the snapshot building and writing in that same iteration's `finally` — so a poll whose
recovery is fatal still writes its snapshot before the exception propagates, and a normal `stop` does not write an
extra one beyond the polls actually executed. Two new module-level functions, called by their bare names so a
frozen check's `patch.object(B, name, ...)` reliably intercepts them: `health_snapshot(health, reconnect_count,
poll_s, clock)` builds the ten-key dict (`at`, `monotonic`, `pid`, `process_started_at`, `connected`, `pong_count`,
`envelope_count`, `reconnect_count`, `last_activity_age_s`, `poll_s` — nothing else, no payloads/ids/tokens/
hostnames); `process_started_at` is a module-level constant computed once at import (fixed for the process's
life). `write_health_observation(path, snapshot)` serializes to JSON, writes a sibling temporary file
(`tempfile.mkstemp(dir=<path's directory>)`) and `os.replace`s it onto the destination, cleaning up the temp file
on any failure path (serialization, the write itself, or the replace) — so a reader never sees a partial file and
none is ever left behind; it returns `True`/`False` and never raises.

**4. Write-failure isolation**: `write_health_observation` already catches its own exceptions internally; the
`finally` block in `run_socket_mode` wraps both the `health_snapshot` *and* `write_health_observation` calls in one
more `try/except` as a second, defensive boundary (needed for a test double that replaces `write_health_observation`
itself with something that raises past its own internal catch, or a `health_snapshot` that raises before a writer
ever runs). A single `failed_streak` boolean, local to `run_socket_mode`, is set on any failed poll (snapshot
raised, the writer raised, or the writer returned `False`) and cleared on any successful write; `S.log(...
"health observation" ...)` is only called on the transition into a new streak (the first failure after a success,
or the very first poll), so a long failing run — or several different failing layers back to back without an
intervening success — logs exactly once per streak, never flooding. Because the whole telemetry attempt lives
inside the `finally` of the `try` that may itself be propagating a recovery exception, and the telemetry code
never lets anything escape that `finally`, a recovery exception is always what actually propagates — a telemetry
failure can never replace or swallow it.

**5. Recovery unchanged**: no change to `_reconnect_or_die`, `_verify_fresh_activity_or_die`, or `SocketHealth.check`
beyond the new counters above; the orchestration added to `run_socket_mode` (the `reconnect_count` bump and the
`finally`-scoped telemetry write) wraps the existing recovery call sites without altering when a recovery is
attempted, what bounds it, or what makes it fatal.

**6. Tests** (`tests/manager/test_bridge_telemetry.py`, new file, 10 tests): each counter in isolation
(`envelope_count`, `pong_count`), a ping not counting as a pong, a repeated/replacement pong value not counted
twice, an envelope counted once, `reconnect_count` accumulating across attempts within one invocation and ending
fatally, the exact ten-key snapshot set, atomic replacement leaving no leftover temporary file (both the success
path and an injected `os.replace` failure that must not damage the destination), and a write failure (an
unwritable directory) that must not change the recovery decision or raise past `write_health_observation`. No
existing test file was modified; all 351 baseline `tests/manager` nodes plus the 10 new ones pass (361 total).

## Rollback

`logs/bridge-health.json` is new, additive, and rewritten wholesale every poll by an atomic replace; a rollback to
pre-b9 `bridge.py` simply stops rewriting it (the file, if present, is inert and read by nothing else). No existing
file, state shape, or credential is touched. `SocketHealth.pong_count`/`envelope_count` and `run_socket_mode`'s
`reconnect_count` are pure additions alongside the unchanged b7 liveness/recovery contract; `observation_path`
defaults to `None`, so any caller that predates this change keeps its exact prior behavior.
