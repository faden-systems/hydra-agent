# b11 notes

## What changed

This attempt continues from the frozen attempt-1 WIP commit (449372e). Three fixes made the ordinary-overage
compaction path (requirement 1) and the held path (requirement 2) actually run: `rollover_enabled()` had stopped
reading `COMPACTION_DEFAULTS`'s `"rollover_enabled": True` default and always evaluated false on an empty
`compaction` config, so every rollover attempt (even the acceptance's default-enabled cases) fell into the held
branch and never called the engine; the held branch itself cleared `pending` instead of keeping it, and never
posted the one-per-episode buildlog line that requirement 2 calls for; and a failed bytes-reason compaction reset
`baseline_bytes` to the current (already-grown) file size, which zeroed `grown` on the next turn and silently
cleared the bytes pending before the retry backoff ever got a chance to retry it. `hydra compact` (`cmd_compact`)
now checks `rollover_enabled` before writing `COMPACT` (holding immediately, exit 1, no live loop) and, with a live
loop, distinguishes `compacted at`, `compaction failed`, `compaction held:` and `compaction unverified` instead of
printing a success-looking line for a held or unverified outcome.

Requirement 3 (the CLI's own compactions) is implemented from scratch: a module-level `cli_compactions_since(data,
offset)` parses `compact_boundary` system records out of a transcript's bytes, and `Supervisor._scan_cli_compactions`
wraps it with the persistent `transcript_scan` offset bookkeeping (reset on a path change or a shorter file,
deduplicated by the record's `at` so a truncate-and-rescan or a repeat scan never double-counts), wired into every
Claude turn (`turn()`, setting `cli_compacted` and feeding `compaction_status_line`'s CLI-last case) and around the
rollover in `run_compaction` (the OLD session's transcript scanned before the id is replaced, the NEW session's
right after).

Requirement 5 (the state digest) replaces `Supervisor.state_block()` with `Supervisor.state_digest(events)`: one
line per track (`now`/`waits_on`/`next_action`, collapsed and cut), the newest 10 founder decisions, `next_gate`/
`waits_on`, and the full JSON of only the tracks selected by this batch's events (thread-ts match, an
`assignee: <name> | track: <id>` first line with or without a leading Slack mention, a `continue <id>:` prefix, or
`work-status.json`'s `track`), bounded to 36,000 bytes for the digest and 40,000 for the whole message, with a
documented degradation order (decisions down to 3, then track lines cut to 120 then 60 bytes, then bare `- <id>`
lines) when the mandatory part alone would exceed 30,000 bytes, and truncation of the touched-track entries in
reverse selection order when the full-entries budget does not fit. `turn()` now prepends this digest for every
engine; `invoke_codex` no longer builds its own duplicate `# factory/state.json` prefix. Every turn record (every
engine, the compaction records included) now carries `message_bytes`, threaded through `invoke()`/`invoke_codex()`
(`self._last_message_bytes`, set to the exact UTF-8 length of the message actually handed to the engine) back up to
`turn()` and to the compaction ledger record in `_finish_rollover_bookkeeping`.

The `state_digest` work (below, under Progress) is not yet landed, so the acceptance's own message-bytes
measurement is not yet available; this section will carry the real measured pair once it is. No real supervisor
session's `logs/turns.jsonl` figure is available in this build-only environment.
