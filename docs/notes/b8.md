## Problem

The manager's Claude engine ran one fresh process per turn; every turn paid cold-start/context-reload cost and
every compaction was a scheduled `/compact`-shaped rollover triggered by an ordinary token/byte threshold. The
founder wants an opt-in persistent process that accepts successive turns over Claude Code's native
`--input-format stream-json` protocol, with automatic rollover narrowed to a genuine emergency (an actual
too-long resume failure on an account already shown working), a credential identity contract gating automatic
account fallback, and `hydra attach` able to park a live background writer instead of refusing outright.

## Implementation

**The vendor boundary.** `Supervisor.invoke` (`manager/supervisor.py`) is the only place that knows about
persistent vs per-turn framing (founder decision 2026-10-05, `docs/architecture.md` §9). It dispatches to
`_invoke_per_turn` (the pre-b8 per-request subprocess, unchanged) or `_invoke_persistent`, and always stops the
previously selected writer before starting a new one (vendor switch to/from Codex, account/model switch, or a
mode rollback to per-turn): `_retire_persistent(category, reason)`.

**`manager/persistent.py`** (new) holds the child-process plumbing only: `spawn()` starts `claude -p
--input-format stream-json --output-format stream-json --verbose [--session-id|--resume] ...` in its own
session/process group, with a background `_LineReader` thread per stream so a startup failure (the process
exits, or times out, before producing the native `system`-typed startup record) is detected *before* any user
request is written to stdin and is never silently replayed (requirement 8). `Child.send(text, timeout)` writes
one stream-json user message and reads until a terminal `result` record, EOF (a crash) or the deadline (a
timeout); `close_orderly()`/`kill_tree()` give `Supervisor.shutdown_persistent()` an orderly-then-forced
teardown (interrupt, a bounded grace, `SIGKILL` the whole process group, wait for `/proc` to clear).

**Persistent lifecycle in `Supervisor`.** `_invoke_persistent` reuses a live child when account/model/session id
all still match, otherwise retires it (a *planned* restart) and starts fresh, trying twice before returning
`None` to signal a startup fallback: the caller (`invoke`) then runs that one turn through `_invoke_per_turn`
instead, posts one buildlog alert, and records the transient fallback in `engine-runtime.json`'s
`configured`/`effective` pair (with a `mode` field alongside the existing `acc`/`model`) so `read_engine_runtime`
and `status_text` show both the configured and the effective mode and the reason; a later successful persistent
start clears it. A crash (child EOF mid-request) or a timeout (deadline exceeded, `kill_tree()`) is an
*unexpected* restart, counted separately from *planned* ones in `persistent-status.json`
(`persistent_status(home)`: `state` `running`/`parked`/`stopped` re-derived from a live pid check — stale
metadata is never reported healthy — `pid`, `account`, `model`, `uptime_s`, `turns_served`, `restarts`).

**Restart safety without a shared process handle.** The live child is an *instance* attribute (`self._persistent`),
never a module-level registry: a reconstructed `Supervisor` (a real restart, or a test simulating one in the
same OS process) owns no pipe to whatever pid `persistent-status.json` last recorded, so `_invoke_persistent`
retires it as an orphan (`SIGKILL` the group, `waitpid` directly since no `Popen` object survived to reap it)
before starting a trustworthy fresh one — this is also what makes the emergency-rollover "old conversation
reaped at the boundary" and the 8.1 "supervisor death" orphan-retirement contracts work with one mechanism.

**Uncertain dispositions (requirement 1/8, PR45 8.1).** A crash (`rc=17`, my `_invoke_persistent` sentinel) or a
timeout (`rc=124`) is distinct from a classifiable engine error: `run_engines` raises
`AllEnginesFailed(errors, uncertain=True)` immediately instead of falling through to the next configured
account (the request may already have had a real side effect) — `AllEnginesFailed.uncertain` is new;
`turn()`'s failure branch, on an uncertain error, calls `mark_handled()` so the event gets a durable
failed disposition instead of being left pending for the ordinary retry-after backoff to resubmit later.
A `logs/in-flight.json` marker, written before `run_engines` is called and cleared in `turn()`'s `finally`,
survives a crash of the *supervisor process itself* mid-request: `Supervisor.run_once()` reconciles a stale
marker on every tick (`_reconcile_in_flight`) by retiring any orphaned live child and giving the marker's exact
events the same durable failed disposition, before anything else runs.

**Identity contract** (`credential_identity`, `observe_identity`, both module-level so tests can patch them):
a credential with no `cred` configured has nothing to verify (`automatic_allowed: True`); one with a `cred` but
no matching, schema-valid, token-bound `<cred>.identity.json` sidecar is unverified. `run_engines` calls
`credential_identity`/`observe_identity` for every Claude attempt: an authoritative observed mismatch
(`observe_identity` returning `token_bound: True` for a different account) blocks even the *primary* selected
account from ever reaching the child; an unverified credential blocks only a *fallback* attempt (switching to a
different account) — the originally selected account still runs, matching every pre-b8 fallback/rotation test.
`observe_identity`'s production default returns `None` (no observation): the founder's 2026-10-05 finding that
the installed CLI does not report token identity is recorded as a fact, not assumed away.
`tests/manager/conftest.py`'s `make_home()` now also writes a verified identity sidecar for both default
accounts (dummy values, same shape b8.regressions.py's own `verified_fixture()` writes) so every existing test
that builds its credentials through it keeps the exact unrestricted fallback behavior it always had.

**Mode** (`read_engine`/`set_engine`/`parse_engine_command`): the engine file gains an optional `mode` key.
`_EnginePair.__missing__` answers `pair["mode"]` with the `per-turn` default without ever materializing the key,
so a legacy/never-touched engine file keeps the exact historical two-key `{"acc", "model"}` shape for every old
caller that compares the whole dict or serializes it — once a mode is ever explicitly set it becomes a real,
persisted key and survives later account/model-only changes (and vice versa). `hydra engine`/the Slack `engine`
command accept `mode=persistent|per-turn` (invalid values rejected atomically, nothing written); their reply
text and `status_text`'s engine line append `mode_suffix(pair)` — a bracket shown only once a mode has ever been
touched (`"mode" in pair`, never the lazy default) — so the four pre-b8 bridge/CLI tests that assert the exact
legacy reply text (no bracket) stay byte-compatible.

**Emergency-only rollover** (requirement 6). `compaction_due()` no longer evaluates the old token/byte
`pending` ratio/quiet-hours trigger at all — only `forced` (`COMPACT`/`hydra compact`, unchanged) or a qualified
`emergency_pending`. That flag is armed in `run_engines` only when a Claude attempt classifies as
`prompt_too_long` **and** the exact (account, model, credential-content) triple has previously completed a
successful turn (`_mark_working`/`_is_working`, keyed by a hash of the credential's current token so replacing
the credential — even with freshly re-verified metadata — can never inherit the old credential's working proof).
`run_emergency_rollover()` (new; `run_compaction()` is untouched and still serves the manual/forced path) retires
any live writer for the old conversation, then atomically replaces the session id — there is no memory-writing
turn here, unlike manual compaction: the triggering request already proved the old conversation cannot accept
another turn. Failure keeps the old id and backs off (`failed_at`/`retry_after_s`, the existing mechanism);
success clears `emergency_pending` and reuses the existing rollover-intent/checkpoint machinery so restart
bookkeeping, verification and durable memory preservation are identical to the manual path.

**Daily restart** (requirement 4): `Supervisor.maybe_daily_restart()`, called every `run_once` tick including a
tick with no queued event, retires a live persistent child once per quiet-hour date
(`config.persistent.daily_restart`, default true only in persistent mode) — deferred (a plain `writer_status`
read, not a lock) while an attach or a turn holds `WRITER`; the completed date persists in
`logs/daily-restart.json` so a supervisor restart on the same date never repeats it.

**`hydra attach`** (requirement 5): now waits (polling, `HYDRA_ATTACH_WAIT_TIMEOUT`, default 10s so the existing
`test_attach_refuses_while_held` baseline still times out quickly against a WRITER held for the test's whole
duration) instead of refusing immediately, parks (kills) any live persistent writer before starting the
interactive process — cross-process, so this is a signal (`SIGTERM` then `SIGKILL`), never
`shutdown_persistent`'s orderly pipe-close — and records the interactive child's pid in
`logs/attach-child.pid` before waiting on it. `Supervisor._reconcile_attach_orphan()` (every tick) retires that
pid if `WRITER` has gone stale (attach's own process died abnormally) before the next event runs, so an
abnormal attach exit still resumes supervisor service.

**`split_handoff` own-line fix.** The manager's own prompt instruction text ("End with `---HANDOFF---` and the
five lines") contains the literal marker mid-sentence; `b8.fake.py`'s deterministic fixture echoes the whole
wrapped prompt back as its reply, which made the old substring-based `split_handoff` cut the reply at that
instruction instead of a real handoff, silently losing the actual reply content. `split_handoff` now requires
the marker on its own line (`HANDOFF_LINE_RE`, matching manager/CLAUDE.md's documented contract exactly) —
behavior-identical for every real handoff (always written on its own `print('---HANDOFF---')` line) and fixes a
latent bug this fixture happened to expose.

## Rollback

Unchanged from b7: `mode` defaults to (and an operator can always set) `per-turn`, which is the exact pre-b8
per-request code path (`_invoke_per_turn`), so no deployment change is required to roll back — set
`engine mode=per-turn` (or leave it untouched) and the persistent plumbing is never invoked. Reverting this
candidate on `main` restores the pre-b8 `supervisor.py`/`bridge.py`/`hydra`; no schema or on-disk format this
candidate introduces (`persistent-status.json`, `logs/in-flight.json`, `logs/attach-child.pid`,
`logs/daily-restart.json`, `logs/working-accounts.json`, the `mode` key in `engine`) is read by the pre-b8 code,
so a rollback needs no migration.
