## Problem and outcome

The deployed supervisor (421b7bd9 spec tip; b10 build aad5f1e7 live) chooses engines by ACCOUNT: `ENGINE_ORDER =
("claude-r2d2", "claude-l", "codex")` rotated to start at the current account, the model carried over by
`carry_model`, and on a credits/usage-limit failure every configured non-Fable model (`engine_fallback.claude_models`,
default `["claude-sonnet-5"]`, b7 requirement 12) retried once on the SAME account before the next account. That is
how the manager ran on claude-l / claude-sonnet-5 from 2026-10-09 18:03Z until the founder's interim change on
2026-10-11 (episode 66e6bd44-5ad1-49e8-84ea-9dd079df25cb): a Fable credits failure on r2d2 moved to l, and l's Fable
credits failure downgraded to Sonnet 5 on the same account. Any alias in `models.json` (sonnet5, haiku4.5, opus5)
can be selected with `@manager engine` or `hydra engine`, and an automatic switch between families guesses the model
by alias name.

Outcome: the manager runs only on a configured ALLOWLIST with a PREFERENCE ORDER, the ladder: by default tier 1
Fable 5.1 on claude-r2d2 then claude-l, tier 2 GPT-6 Astra on codex, tier 3 Opus 5.5 on claude-r2d2 then claude-l;
the last tier is the floor. Automatic fallback walks the ladder (a tier's model on each of its accounts, then the
next tier) and never lands below the floor; a command that names a model outside the ladder is refused with a
one-line reason and changes nothing; when every allowed step fails the manager posts one top-level `manager
unavailable: all allowed engines failed (<reasons>)` line and retries on the normal back-off, never downgrading;
`hydra status` shows the floor and the active tier, and every fallback notice names the tiers; `models.json` loses
the sonnet5 and haiku4.5 aliases and gains `gpt6.1`/`sol6.1 -> gpt-6.1-sol` for coder use (outside the manager
ladder); frozen tests cover each failure path and prove no model outside the ladder is ever invoked (nothing below
the floor is ever recorded in `logs/attempts.jsonl`).

This supersedes b7 requirement 12 (the same-account non-Fable model retry and the `engine_fallback.claude_models`
list; the key is ignored from now on, requirement 1) and the sentence of b7 requirement 12 / `manager/README.md`
that an automatic switch "keeps the alias when the new family has it, else takes the family default": the ladder
decides the model. The b7 frozen acceptance's `fallback_matrix` (a merged, closed loop's harness) pins the old retry
and is not run by this exit. Everything else of b7 requirement 11/12 (classification, `logs/attempts.jsonl`, one
notice per fallback episode surviving a crash) and of b8 (persistent mode, the identity gate, the emergency
rollover) stays in force.

## Requirements

1. The ladder. `manager/supervisor.py` defines the module-level constant `MANAGER_LADDER`, a tuple of tiers in
   preference order, each `{"model": <full model id>, "accounts": (<account>, ...)}`:
   `claude-fable-5-1` on `("claude-r2d2", "claude-l")`, then `gpt-6-astra` on `("codex",)`, then `claude-opus-5-5`
   on `("claude-r2d2", "claude-l")`. `manager_ladder(config, models=None, engines=None)` returns the ladder in force:
   `config["engine_policy"]["ladder"]` when it is a non-empty list of such entries whose every account is a known
   engine name (the `engines` map, `default_engines` by default) and whose every model resolves through
   `resolve_model` for that account's family (an alias or a full id; the result is the full id) AND
   belongs to the immutable founder-approved set `{claude-fable-5-1, gpt-6-astra, claude-opus-5-5}`.
   Config and home model aliases can narrow or reorder this set but cannot extend it. Any resolved model outside
   that set invalidates the entire override (the diagnostic names that model). Every invalid override falls back
   to `MANAGER_LADDER` with exactly one `log` line per process naming the first problem (`engine_policy ignored:
   <reason>; the default ladder is in force`); the same reason is shown by status (requirement 4). A tier's accounts
   keep their listed order; a model may appear in more than one tier only on different accounts; an entry naming a
   model of the wrong family for one of its accounts invalidates the whole configured ladder. `ladder_steps(ladder,
   engines)` is the flat list of `(tier_number, account, model)` in ladder order (tier numbers start at 1), limited
   to accounts present in `engines` with a `bin`. `floor_model(ladder)` is the last tier's model.
   `ladder_position(pair, ladder)` returns the 1-based tier number whose model equals `pair["model"]` and whose
   accounts include `pair["acc"]`, else None. `Supervisor.engine_ladder()` returns `manager_ladder(self.config,
   self.models, self.engines)`. `Supervisor.run_engines` tries the steps in ladder order rotated to start at the
   configured primary (the runtime `configured` pair during an active fallback episode, otherwise the JSON
   engine file; an explicit selection replaces that primary and closes the old episode as today): that pair's own
   step first, then every other account of its tier in listed order, then every lower tier (toward the floor) in order, then the tiers above it from the top (the cyclic
   rotation of `engine_order` today, at tier granularity, so a deliberately selected lower tier still falls back
   and still recovers upward). A configured pair that is not a ladder step (a stale engine file from before this
   loop, a hand edit, an account the ladder does not list) is never invoked: the rotation starts at the first step
   whose account equals the configured account, or at the ladder's first step when none does, with one `log` line
   per turn (`engine policy: configured <label> is outside the ladder; starting at tier <k> <label>`). Each step
   invokes exactly that step's model on that step's account (`carry_model` is no longer consulted by `run_engines`;
   the function stays for callers that predate this loop). Per step, unchanged from today: the identity gate
   (a token identity mismatch is recorded as an `auth` attempt and skipped; an unverified credential is skipped
   when switching TO it), the budget check (`over budget`, persisted switch), `preamble_for`, the transition read
   at a family switch, the Codex `[flush]` line, `record_attempt` for every attempt, `_mark_working` on success,
   the `engine:` note when the winning account differs from the configured one, and `AllEnginesFailed(...,
   uncertain=True)` on rc 17/124 with no further step. Failure handling per step: `credits`, `usage_limit` and
   `auth` mark the switch persist-worthy and move to the next step; `rate_limit` and `other` move to the next step
   without persisting; `prompt_too_long` skips every remaining Claude-family step (tier 3 included) and sets the
   emergency pending exactly as today. The same-account different-model retry is gone: `engine_fallback.claude_models`
   is never read as a retry list (when the key is present in config, one `log` line per process says it is ignored
   since b12). On success at a step other than the configured pair with a persist-worthy failure before it,
   `set_engine(..., explicit=False)` records the winning pair and `_note_fallback_transition` runs as today. Nothing
   outside the ladder is ever invoked, so `logs/attempts.jsonl` never carries a model outside the ladder in force.
2. Commands refuse what the ladder does not allow. `enforce_engine_policy(pair, ladder)` raises `BadEngine` with
   exactly one line when `ladder_position(pair, ladder)` is None: `model <id> is not on the manager's allowlist
   (floor <floor model>); allowed: <model> on <acc, acc>; <model> on <acc>; ...` (the ladder in force, tiers in
   order, full ids). `hydra engine ...` and `@manager engine ...` resolve the command with `parse_engine_command`
   as today (an unknown alias or a wrong-family model keeps today's one-line reasons), then call
   `enforce_engine_policy` on the resulting pair BEFORE `set_engine`: a refused command prints/replies the reason
   followed by `; nothing changed (engine: <current label>)` (exit 2 on the console, a reply in Slack) and leaves the
   engine file and `engine-runtime.json` untouched. A legacy `engine <account>` form means the family default model
   and is allowed when that default is on the ladder for that account; `mode=persistent|per-turn` alone keeps the
   account and model and is allowed when the current pair is on the ladder; `engine` alone prints the current pair
   unchanged (`hydra engine` prints the same single line as today; the policy line lives in `hydra status`).
   `hydra attach` refuses (exit 2, the same one-line reason, no process started) when the engine file's pair is
   outside the ladder. Carry-over never lands below the floor: automatic switches between accounts and families are
   ladder steps only (requirement 1), so the floor is the lowest model any path can reach.
3. When every allowed step fails, no downgrade. On `AllEnginesFailed` the turn keeps today's bookkeeping (the
   `error` turn record, `logs/retry-after` at `RETRY_AFTER_S`, the failed reaction, events left pending; an
   uncertain crash/timeout keeps its durable disposition) and posts, instead of the per-thread `manager unavailable
   (every engine failed), will retry` note, ONE top-level dev-channel line per unavailability episode through the
   outbox (`_queue_notice_once`, deduplicated across a restart): `manager unavailable: all allowed engines failed
   (<reasons>)` where `<reasons>` lists every ladder step in the order tried as `tier <k> <acc> (<model>): <what>`
   joined by `; `, `<what>` being the attempt's classification (`credits`, `usage_limit`, `auth`, `rate_limit`,
   `prompt_too_long`), `crash`/`timeout` for rc 17/124, `other: <first 80 characters of the error>` otherwise, or
   `skipped: <why>` for a step not invoked (unverified credential, over budget, identity mismatch, skipped Claude
   family), the whole parenthetical cut to 1,000 characters on a character boundary. An episode starts at the
   first failing turn (`logs/unavailable.json` `{"episode_id": <uuid>, "since": <iso>, "turn": <n>, "reasons":
   <text>}`, written before the notice is queued, the notice id `unavailable-<episode_id>`) and ends at the next
   turn served by any ladder step (the file's `episode_id` set to null; no "available again" line, the thread reply
   itself shows the manager is back); a retry that fails again inside the same episode posts nothing more. The CLI
   reply file for a founder console event and the `logs/self-replies.jsonl` record for an unroutable self event
   keep today's behaviour with the new wording. The retry is the normal back-off: the next tick after
   `logs/retry-after` expires tries the ladder again from the top of the rotation.
