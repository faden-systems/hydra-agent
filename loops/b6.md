# Loop B6 - Heartbeat reaction, direct posts join threads, `hydra update` runs git as hydra

## Purpose
Three small things from the first day of b5 in use. (1) The founder wants the working indicator to show the manager
is alive during a long turn: alternate the reaction every 20 seconds while the turn runs. (2) Issue #24: posts the
manager makes directly from inside a turn bypass the supervisor's own-post bookkeeping, so the thread is never joined,
later replies there are lost, and the post is not mirrored. (3) Issue #24 comment: `hydra update` run as root fails
git's ownership check on the `hydra`-owned clone; the git steps must run as `hydra`, only the copy and restarts as
root.

## 1. Heartbeat reaction (supervisor)
- While a turn runs, every `reactions.heartbeat_seconds` (default 20) the supervisor swaps the reaction on each
  triggering message between `eyes` and `hourglass_flowing_sand` (remove one, add the other). On delivery the current
  one is removed, as in b5. The failure `x` is unchanged.
- Implemented as a background ticker started when the turn starts and stopped before delivery; it uses the
  supervisor's injectable `sleep`/`now` so tests run in real but short time (`heartbeat_seconds` can be fractional).
- `reactions.heartbeat_seconds: 0` disables the swap (plain b5 behaviour). Config in `config.json`.
- Rate: one `reactions.add` and one `reactions.remove` per message per interval; with a batch of three messages that is
  six calls every 20 s, well inside Slack's limits. A failing swap is logged once per hour and never blocks.
- Failures: a failed remove does not stop the add that follows; the recorded reaction is the name of the last add
  attempted; delivery removes that name and treats Slack's `no_reaction`/`already_reacted` as done. The once-per-hour
  log throttle is one key for all reaction failures, as in b5.

## 2. Direct posts join the thread and are mirrored (bridge + supervisor)
- Every post the manager makes, whether the supervisor delivers a reply or the engine calls the Slack tool itself
  inside a turn, goes through one path: `bridge.post(channel, thread_ts, text)` which posts, calls
  `note_own_post`, and mirrors the line with its `thread_ts`. The engine is given that path as its posting tool
  (the `hydra post` CLI subcommand writes to a `inbox/outbox.jsonl` that the bridge drains and posts through the same
  function); direct `chat.postMessage` from the engine's own tools is not configured.
- Rule text appended to `manager/CLAUDE.md`: "To post to Slack from inside a turn, use `hydra post <channel>
  <thread_ts|-> <text>`; never call the Slack API directly."
- `-` posts a new top-level message; the `ts` the poster returns (`SlackPoster` returns Slack's answer) becomes the
  joined thread and the mirror line's `thread_ts`, so replies to it reach the manager. A poster that returns nothing
  (dry mode) records no join.
- `threads.json` and the mirror reflect direct posts; `status` counts them.

## 3. `hydra update` privilege split
- `hydra update` run as root: `git fetch`/`checkout`/`pull` executed as `hydra` (`sudo -u hydra -H git -C ...`), then
  the copy into `app/`, the `AGENTS.md` link and the `systemctl restart`s as root. Run as `hydra`: it does the git
  steps and prints the exact root command for the rest instead of failing. The `safe.directory` workaround is not
  needed and the runbook drops it.

## Tests (`tests/manager/`)
Heartbeat sequence with a fractional interval and an engine that takes several intervals (eyes, hourglass, eyes,
..., removed at delivery); disabled with 0; failing swap tolerated. Outbox drain: `hydra post` writes a line, the
bridge posts it, records the join, mirrors with `thread_ts`. `hydra update` as root uses `sudo -u hydra` for git
(recorded by a fake `sudo` on PATH) and as `hydra` prints the root command and exits 0 after the git steps.

## Exit criteria
`loops/b6.exit.sh`: base and harness preflight; fence (`manager/`, `tests/manager/`, `setup/manager-vm.md`,
`setup/manager-vm.sh`); the full posting rule in `manager/CLAUDE.md`; pytest; the exit-owned `loops/b6.acceptance.py`:
with `heartbeat_seconds=0.5` and a fake engine taking ~1.7 s, the recorder sees `add eyes`, then strictly alternating
`remove <standing>`/`add <other>` pairs (two to four swaps), then a final `remove` of the standing name after the poster
is called, and no add after delivery; a reactor whose remove raises still lets the turn and the delivery complete; with
`0` only add/remove eyes; `hydra post` round trip through the outbox into the poster with `note_own_post` recorded in
`threads.json`, the mirror line carrying `thread_ts`, a reply in that thread queued, and `-` joining the thread at the
ts the poster returns; `hydra update` with recording fakes for `sudo`, `systemctl` and `git` (the fake git logs the
user it ran as, then runs the real git) against a remote that moved after the clone: as root (`HYDRA_FAKE_UID=0`)
every git step runs via `sudo -u hydra`, the newer commit is installed and `AGENTS.md` links to it; unprivileged, the
git steps run directly, the clone is updated, `app/` is untouched, nothing is restarted and a line matching
`sudo [-n] hydra update` is printed; then b1 to b5 acceptance still pass.

## After merge (manager assigns Hermes)
`sudo -n hydra update` as `hermes`; a question to the manager that takes more than 20 s (ask it to summarize
`MEMORY.md`) and watch the reaction alternate; a direct post from a turn (`hydra post`) appears in the thread, joins
it, and is in the mirror.
