## Problem and outcome

b7 requirement 1 keeps the bridge healthy on fresh pongs alone, but nothing observable proves that a quiet interval
(no Socket Mode envelopes, no reconnects) was in fact carried by pongs: `SocketHealth` records freshness only in
private fields, the journal has no pong entries, and systemd uptime cannot show that an interval was envelope-free.
Founder decision 1791142113.617989 accepted blocks-only; idle-pong is the single open b7 item. Outcome: the
existing monitor also writes a metadata-only status file every poll, and one bounded 15-minute observation shows a
stretch over 5 minutes with no envelopes and no reconnects in which the same connected process kept counting pongs.

## Requirements

1. Counters on `SocketHealth`: `envelope_count` increments once per `note_envelope` call (the raw receipt
   listener, before Bolt filtering, any arguments). `pong_count` increments once per *changed*
   `client.current_session.last_ping_pong_time` observed at a check; an unchanged value never increments, and a
   replacement session carrying the same old timestamp does not increment. Outbound pings and Web API calls are
   invisible to the monitor and must stay so: nothing the bridge sends changes either counter. Counters start at 0
   per process and never reset while the process lives. The counters are exposed as integer attributes
   `pong_count` and `envelope_count` and by `counters()` returning `{"pong_count", "envelope_count"}`.
2. `run_socket_mode` counts recovery attempts: `reconnect_count` increments once per attempt, before the
   attempt's outcome is known, so a fatal attempt is still counted in the last snapshot written.
3. Observation file: `run_socket_mode(handler, stop, clock=..., poll_s=10, reconnect_timeout_s=30,
   observation_path=None)`; `serve()` passes `<home>/logs/bridge-health.json` (a frozen check drives the production
   bridge `main` with the b7 fake network boundaries and requires that file to be written by the real monitor).
   Every poll iteration writes exactly one snapshot, in that iteration's `finally`, after the health check and any
   recovery: so a poll whose recovery is fatal still writes its snapshot, and a normal stop writes nothing beyond
   its poll's snapshot. The monitor calls `health_snapshot(health, reconnect_count, poll_s, clock)` and
   `write_health_observation(path, snapshot)` by those module-level names in `manager/bridge.py` (frozen checks
   intercept them there; no local aliases). `write_health_observation` writes a sibling temporary file in the same
   directory, then `os.replace`, so a reader never sees a partial file and no temporary file is left behind. The
   snapshot has exactly these keys: `at` (UTC ISO 8601 ending in `Z`), `monotonic` (float from the monitor
   clock), `pid`, `process_started_at` (UTC ISO 8601, fixed for the life of the process), `connected` (bool),
   `pong_count`, `envelope_count`, `reconnect_count` (non-negative ints), `last_activity_age_s` (float >= 0: the monitor clock at
   snapshot time minus the last inbound activity time, so with an injected clock it grows by exactly the injected
   advance) and `poll_s`. Nothing else: no payloads, channel or user ids, URLs, tokens, environment values or hostnames.
4. Write-failure isolation: `run_socket_mode` wraps snapshot construction and writing in ONE telemetry-only
   exception boundary, and `write_health_observation` independently catches its own write exceptions and returns
   False (it returns True or False and never raises). A failed poll is one where the snapshot raised, the writer
   raised, or the writer returned False. Across ALL layers (snapshot construction, serialization, temporary file,
   replacement) the bridge emits at most one `S.log` line containing `health observation` per failure streak,
   where a streak is a maximal sequence of consecutive failed polls within one monitor invocation; a successful
   write ends the streak and the next failed poll starts a new one, logged again. The deterministic sequence
   fail, fail, ok, fail, fail yields exactly two lines, for each layer. Telemetry failures never change the health
   result, the recovery decision or the monitoring loop, and a recovery exception is never replaced by a telemetry
   one.
5. Unchanged recovery behaviour: every b7 liveness and recovery contract passes unchanged. The exit runs the
   baseline `loops/b7.acceptance.py` in full and preserves every statement of the baseline `tests/manager`
   suite structurally (no exemptions); new tests may be added. The frozen acceptance adds the two B4
   regressions of `loops/b7.md` that the inherited checks did not pin: a connected but stale client is recovered
   with `connect_to_new_endpoint(force=True)`, and a reconnect that returns connected with only the old pong and
   no new envelope is fatal within the grace bound.
6. Candidate tests in `tests/manager` cover: each counter; a ping does not count as a pong; a repeated pong value
   is not counted twice; an envelope is counted once; `reconnect_count`; the exact snapshot key set; atomic
   replacement without a leftover temporary file; write failure isolated from health decisions. The frozen
   acceptance asserts the same through the public seams above.
7. Deployment (bridge-only, privileged): the service executes the copied tree under `$HYDRA_APP`
   (`/srv/hydra/manager/app/manager`, root-owned), not the Git checkout, and `hydra update` restarts both services,
   so it is not used here. The installed bridge is `$HYDRA_APP/bridge.py`, which today resolves to
   `/srv/hydra/manager/app/manager/bridge.py` (`HYDRA_APP` already names the copied `manager/` directory). Hermes,
   as `hydra`, fetches the exact merged SHA into `/srv/hydra/repos/hydra-agent`
   (`git fetch origin && git merge-base --is-ancestor <SHA> origin/main`); before copying, resolves the target as
   the script path in the service's `ExecStart` (`systemctl show hydra-bridge -p ExecStart`) and requires it to
   equal `$HYDRA_APP/bridge.py`; then with root writes that commit's `manager/bridge.py` over that single file
   (`git show <SHA>:manager/bridge.py`, mode and ownership preserved) and verifies `sha256sum` of that same path
   equals the digest of `git show <SHA>:manager/bridge.py`; then performs the single `systemctl restart
   hydra-bridge`; then records in
   the track thread the merged SHA, the installed-file digest, the new bridge PID
   (`systemctl show hydra-bridge -p MainPID`) and the restart time, and confirms `logs/bridge-health.json`
   appears within 30 seconds with `pid` equal to that MainPID. No second restart inside this loop; hydra-manager is
   not restarted; nothing else under `$HYDRA_APP` changes.
8. Observation: Hermes runs the frozen `loops/b9.observe.py --path $HYDRA_HOME/logs/bridge-health.json
   --minutes 15 --interval 10 --out <evidence dir> --deployed-sha <SHA>` on the VM. It samples the file every
   10 seconds, records observer monotonic time with every sample (spans, gaps and the deadline use monotonic time;
   wall time is the human record), writes `samples.jsonl` and `verdict.json`, and prints the verdict. A sample is
   eligible only when it is well-formed (object with exactly the required keys present, positive integer `pid`,
   non-negative integer counters, boolean `connected`, finite non-negative `last_activity_age_s`, positive
   `poll_s`, finite `monotonic`, non-empty `at` and `process_started_at`, and no other key), `connected` is true
   and `last_activity_age_s` is below 300; malformed metadata, including any extra key, is recorded as an error
   sample with the reason, never silently projected. A quiet run starts only at an eligible
   sample and extends while every sample stays eligible, `pid` and `process_started_at` never change,
   `envelope_count` and `reconnect_count` never change, `pong_count` never decreases, and the monotonic gap
   between consecutive samples never exceeds three sampling intervals. `observed` requires, inside one run, a
   prefix spanning more than 300 seconds of observer monotonic time whose `pong_count` rose and whose file was
   actually being rewritten over that prefix (at least one distinct `at` value per two polls on average); the
   earliest qualifying interval is retained in `verdict.json`. Anything else is `not observed`, with every run,
   the reason it broke (`envelope received`, `reconnect attempted`, `process changed`, `disconnected`,
   `activity stale`, `sampling gap`, `malformed: ...`, an unreadable-file error, or `end of collection`) and,
   for runs that did not qualify, the explicit reasons (`span too short`, `flat pongs`, `insufficient
   rewrites`). A run broken by an envelope is a normal busy channel, not a defect.
9. Closure (durable evidence): `verdict.json` has exactly `verdict`, `evaluation` (the complete output of the
   observer's evaluation, verbatim), `samples_sha256` and `metadata` (`path`, `minutes`, `interval_s`,
   `deployed_sha`, `observer_host_pid`, `systemd`). Hermes leaves `samples.jsonl` and `verdict.json` on the VM;
   the manager commits both under `factory/evidence/b9/<deployed-sha>/` in faden-systems/faden and runs the frozen
   observer at BASE_REF (`git show <BASE_REF>:loops/b9.observe.py` as `--closure-check <evidence dir>`), which
   recomputes from `samples.jsonl` with the recorded `interval_s` and requires every recomputed field
   (`evaluation`, field for field, and `samples_sha256`) to equal the recorded one and `verdict` to equal
   `evaluation.verdict`; the manager separately checks `metadata.deployed_sha` equals the merged candidate SHA
   and every sample's `pid` equals the recorded bridge MainPID, and records the evidence commit SHA, the deployed
   SHA, the installed bridge digest and the bridge PID/`process_started_at` identity in the b track log before
   closure.
   `observed` closes the b7 idle-pong item with the single founder-requested top-level line. `not observed` is
   reported truthfully in the b thread; another collection window is a founder decision, not a new coding attempt.
