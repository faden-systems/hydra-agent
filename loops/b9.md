## Problem and outcome

b7 requirement 1 keeps the bridge healthy on fresh pongs alone, but nothing observable proves that a quiet interval
(no Socket Mode envelopes, no reconnects) was in fact carried by pongs: `SocketHealth` records freshness only in
private fields, the journal has no pong entries, and systemd uptime cannot show that an interval was envelope-free.
Founder decision 1791142113.617989 accepted blocks-only; idle-pong is the single open b7 item. Outcome: the
existing monitor also writes a metadata-only status file every poll, and one bounded 15-minute observation shows a
stretch over 5 minutes with no envelopes and no reconnects in which the same connected process kept counting pongs.

## Requirements

1. Counters on `SocketHealth`: `envelope_count` increments once per `note_envelope` call (the raw receipt
   listener, before Bolt filtering, any arguments). `pong_count` increments once per *changed*
   `client.current_session.last_ping_pong_time` observed at a check; an unchanged value never increments, and a
   replacement session carrying the same old timestamp does not increment. Outbound pings and Web API calls are
   invisible to the monitor and must stay so: nothing the bridge sends changes either counter. Counters start at 0
   per process and never reset while the process lives. The counters are exposed as integer attributes
   `pong_count` and `envelope_count` and by `counters()` returning `{"pong_count", "envelope_count"}`.
2. `run_socket_mode` counts recovery attempts: `reconnect_count` increments once per attempt, before the
   attempt's outcome is known, so a fatal attempt is still counted in the last snapshot written.
3. Observation file: `run_socket_mode(handler, stop, clock=..., poll_s=10, reconnect_timeout_s=30,
   observation_path=None)`; `serve()` passes `<home>/logs/bridge-health.json`. After every monitor poll (after the
   health check and any recovery) the monitor writes one snapshot by `write_health_observation(path, snapshot)`:
   write a sibling temporary file in the same directory, then `os.replace`, so a reader never sees a partial file
   and no temporary file is left behind. The snapshot comes from `health_snapshot(health, reconnect_count, poll_s,
   clock)` and has exactly these keys: `at` (UTC ISO 8601 ending in `Z`), `monotonic` (float from the monitor
   clock), `pid`, `process_started_at` (UTC ISO 8601, fixed for the life of the process), `connected` (bool),
   `pong_count`, `envelope_count`, `reconnect_count` (non-negative ints), `last_activity_age_s` (float >= 0) and
   `poll_s`. Nothing else: no payloads, channel or user ids, URLs, tokens, environment values or hostnames.
4. Write-failure isolation: any exception while building or writing the snapshot is caught inside the writer,
   logged through `S.log` at most once per failure streak, and never changes the health result, the recovery
   decision or the monitoring loop. `write_health_observation` returns True or False and never raises.
5. Unchanged recovery behaviour: every b7 liveness and recovery contract passes unchanged. The exit runs the
   baseline `loops/b7.acceptance.py` in full and preserves every statement of the baseline `tests/manager`
   suite structurally (no exemptions); new tests may be added.
6. Candidate tests in `tests/manager` cover: each counter; a ping does not count as a pong; a repeated pong value
   is not counted twice; an envelope is counted once; `reconnect_count`; the exact snapshot key set; atomic
   replacement without a leftover temporary file; write failure isolated from health decisions. The frozen
   acceptance asserts the same through the public seams above.
7. Deployment: after merge Hermes deploys with ONE bridge restart (`systemctl restart hydra-bridge`), records the
   deployed full SHA (`git rev-parse HEAD` of the deployed checkout) and the new bridge PID in the track thread,
   and confirms `logs/bridge-health.json` appears within 30 seconds. No second restart inside this loop.
8. Observation: Hermes runs the frozen `loops/b9.observe.py --path $HYDRA_HOME/logs/bridge-health.json
   --minutes 15 --interval 10 --out <evidence dir> --deployed-sha <SHA>` on the VM. It samples the file every
   10 seconds, writes `samples.jsonl` and `verdict.json`, and prints the verdict. `observed` requires one
   continuous run of samples spanning more than 300 seconds of observer time in which: `pid` and
   `process_started_at` never change, `connected` is true in every sample, `envelope_count` and
   `reconnect_count` never change, `pong_count` never decreases and is strictly greater at the end than at the
   start, `last_activity_age_s` is below 300 in every sample, and the file was actually being rewritten (at
   least one distinct `at` value per two polls on average). Anything else is `not observed`, with the longest
   candidate run and the reason it broke. A run broken by an envelope is a normal busy channel, not a defect.
9. Closure: the manager validates the evidence directory against the deployed SHA (same SHA as the merged
   candidate, hashes of `samples.jsonl` recorded in the b track log) and the verdict. `observed` closes the b7
   idle-pong item with the single founder-requested top-level line. `not observed` is reported truthfully in
   the b thread; another collection window is a founder decision, not a new coding attempt.
