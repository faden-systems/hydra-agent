## Problem

Three defects of the supervisor's own bookkeeping cost most of 2026-10-18 (rows in the appendix).

1. A rollover that worked was recorded as failed. The 14:54Z rollover (52164f18 -> a0023f84, 305,024 context
   tokens before) shrank the context: the new session's first request was about 30k tokens (cache creation 15,407
   plus cache read 14,201). But `verify_compaction` takes the next measured Claude turn's `context_tokens`, and
   the first turn on the new id (turn 2136) timed out at 1800 s with nothing measured; the first measured turn
   (2137) reported 343,387, because its first request already carried everything turn 2136 had done. The
   verification recorded `ok: false` ("context tokens still 343387 after rollover"), `failed_at` armed the six-hour
   back-off, and every tokens-based compaction was blocked while the context grew to 785,018 (turns 2141-2144)
   until a forced compaction at 17:40Z. The number verified was the wrong number.
2. A forced compaction failed on the reply's shape. At 17:37Z the `[compaction]` turn did what `COMPACTION_MESSAGE`
   asks ("reply only `compacted`"), but `run_compaction` requires the reply to carry a valid five-line
   `---HANDOFF---` block: "the memory-writing turn produced no valid five-line handoff", session kept, `failed_at`
   re-armed. MEMORY.md had been written. The message and the code disagree, and a disagreement of that kind cost an
   engine turn and a six-hour hold (the forced retry at 17:40Z took).
3. The manager's own long turns were treated as account faults. Turns 2136, 2138, 2139 and 2140 (15:24Z to 17:13Z)
   each ran the full 1800 s because the manager waited inside the turn on long runs; the supervisor recorded each
   rc 124 as classification `other`, counted them as faults on tier 1 claude-r2d2, escalated the episode at
   17:13:55Z ("engine fault escalated ... timeout") and moved to claude-l, which then served a 536 s turn at 688k
   tokens without trouble. The same happened once more at 23:46Z (turn 2182). Nothing was wrong with the account;
   a turn that ran out of time while working was indistinguishable from an engine that hung.

## Requirements

1. Verification by the new session's first request. After a rollover, the outstanding verification
   (`logs/compaction.json: verify`) is settled from the new session's transcript whenever that file exists, never from a turn's stdout:
   the supervisor's own callers pass `verify_compaction` no measurement; it then locates the transcript of `verify.new_id`
   (`find_claude_transcript` under the engine's config dir, as the b11 scan does) and reads the first `assistant`
   record's usage with `_context_tokens_from` (input + cache creation + cache read, each once). That number is
   `after_tokens`; `ok` is `after_tokens < threshold_tokens`; the record carries `source: "transcript"`. When the
   transcript exists but has no assistant record yet, the verification stays pending with `ok: null` as today
   (requirement 4/13, loops/b7.md: a missing measurement never settles it), whatever the turn measured. When no
   transcript file of `verify.new_id` exists at all (an engine that writes none: the offline fakes of the baseline b11
   tests report their context on stdout only), the turn path's own `context_tokens` settles the verification as it did
   before b15, with `source: "turn"` (amendment 1, 2026-10-19); the real CLI writes its transcript as soon as it
   starts, so a session that ran at all is judged by its first request. It is attempted at every Claude turn's
   end (as today) and at the start of `compaction_due` before its guards, so a first turn that timed out or crashed
   no longer delays it and a pending verification cannot block a due compaction once the file can answer. A later
   turn's own `context_tokens` keeps its b7 role (scheduling the next compaction through `schedule_compaction`) and,
   once a transcript file of the new id exists, never fails or passes a verification. The no-transcript fallback is
   the one exception and is bounded in time and place: it applies at the turn path only (`turn_tokens`, at the end
   of a Claude turn served on the new id), never from `compaction_due`, and only while no transcript file of the new
   id exists; whichever Claude turn first measures a context under that condition settles it (without a transcript
   there is no first request to prefer, and the engine writing none is the b11 fakes' case). An explicit argument (`verify_compaction(<tokens>)`, used by the baseline
   test `test_verify_compaction_unknown_usage_stays_pending_until_measured` and by nothing in the turn path) keeps
   its old meaning and settles the verification with `source: "argument"`. `hydra status`'s compaction line gains `| session start: <S> tokens` right
   after the `context:` number, S being the current session transcript's first assistant usage (the segment is
   absent when the session has no transcript or no assistant record yet; amendment 1 replaced `unknown`, which would
   have changed the byte-identical b11 status pins); the README's one-line description is updated to match.
2. Reply-shape failures of the `[compaction]` turn. (a) `COMPACTION_MESSAGE` states the whole contract: write
   MEMORY.md, update MANAGER-HANDOFF.md, then reply `compacted` followed by the `---HANDOFF---` block with its five
   lines. (b) A shape failure is a `[compaction]` reply (rc 0) that carries no valid five-line handoff or that left
   MEMORY.md's bytes unchanged; the rollover does not happen and the old id is kept, as today (the baseline tests
   `test_missing_handoff_retains_old_id`, `test_incomplete_handoff_is_rejected` and
   `test_identical_content_memory_rewrite_does_not_qualify` stay byte-identical and green, error texts included).
   What changes is the back-off: the first shape failure of a streak leaves `failed_at` as it was, records
   `shape_failures: 1` in `logs/compaction.json` and on the ledger record, keeps the `COMPACT` file when the
   compaction was forced, and the next turn boundary runs the compaction again with `COMPACTION_MESSAGE` followed
   by one sentence naming the miss ("Your previous compaction reply carried no valid five-line handoff; end it with
   the `---HANDOFF---` block." or "Your previous compaction reply left MEMORY.md unchanged; write the durable facts
   to MEMORY.md before replying."). The second consecutive shape failure arms the back-off exactly as today
   (`failed_at`, the one buildlog line per streak, `COMPACT` consumed). A rollover resets the streak. Engine
   failures of the compaction turn (a nonzero return code) are unchanged: they back off at once as today.
3. Turn timeouts apart from account faults. An rc 124 attempt (per-turn `_run` timeout or the persistent child's
   send timeout) is recorded in `logs/attempts.jsonl` with classification `timeout` for a working one and today's `other` for a silent one (the row shape the
   frozen b14 acceptance pins; amendment 1), and with
   `timeout: "working"` or `"silent"` plus `transcript_records: <k>`: k is the number of `assistant` records the
   session's transcript gained between the attempt's start and the kill (the file's record count before and after,
   read with the b11 scan's tolerance: an unreadable or missing transcript counts 0). A **working** timeout (k >= 1)
   keeps b8's uncertain disposition (the events are answered as unavailable, nothing is replayed, the walk stops)
   but never opens, extends, counts in or escalates a fault episode (`logs/fault.json` is untouched) and never
   moves the engine; instead one top-level dev-channel line `manager turn timeout: turn <n> on <acc> (<model>) ran
   <T> s while working (<k> replies); its events were answered as unavailable` is queued (outbox id `timeout-<n>`,
   durable in the turn's ledger row as `timeout: "working"` before it is queued, reconciled at start like the fault
   line). A **silent** timeout (k = 0) is a fault exactly as today (rule 4, the b14 valve with its count,
   escalation and probe) and its fault text stays `timeout` (the exact contract the frozen b12
   acceptance and its baseline test pin; amendment 1): the silent kind is told by the attempt row, the turn row and
   the status line. `hydra status` prints,
   immediately after the compaction line, `last turn timeout: <PDT time> turn <n> working (<k> replies)` or
   `... silent` when a timeout happened within the last 24 h; nothing otherwise.
