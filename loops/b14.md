# b14: the session-in-use repair and the rule-4 safety valve

Owner: manager; founder-authorized manager build (founder 1792181158.788489, 2026-10-16, urgent), no coder.
Reviewed spec PR, frozen exit, build PR, Hermes deploys when idle. Repo: hydra-agent, `manager/supervisor.py`.

## Problem

The outage recurred twice. After a context rollover the first turn on the new session id timed out (1800 s)
or died: on 2026-10-14 17:49Z (ccfd78e6, rc 124, then `Session ID ccfd78e6... is already in use` on both Fable
accounts until the founder's manual marker repair) and on 2026-10-15 23:08Z (8a4e6f56, turn 1766 timed out, then
turns 1773-2007 failed `Session ID 8a4e6f56... is already in use` on claude-l from 00:00Z to 20:06Z on 2026-10-16).
The CLI creates the transcript `$CLAUDE_CONFIG_DIR/projects/<encoded cwd>/<id>.jsonl` as soon as it starts, but
`_mark_session_started` runs only after a successful turn, so `rollover-intent.json` keeps `started: false`, and
every later call uses `--session-id <id>` on an id that already exists, which fails forever. Since b12 (founder
rule 4) a fault never moves the manager, so the second incident was a 20-hour outage with one fault line posted.

## Requirements

1. Resume when the transcript exists. Before a Claude invocation would pass `--session-id <id>` (because the
   rollover intent names `<id>` as `new_id` with `started` false), the supervisor checks
   `find_claude_transcript(<config dir>, <home>, <id>)`; when the transcript file exists it marks the session
   started (`_mark_session_started`) and invokes with `--resume <id>` instead. Both invocation paths (per-turn
   and persistent) follow this rule. An id with no transcript still starts with `--session-id` (b7 requirement
   13 unchanged). The check runs at the next invocation only, after the runner has retired the previous process
   (a timed-out per-turn process is killed by the runner's timeout; a persistent child is retired by the existing
   lifecycle) and after the timed-out turn received its durable uncertain disposition (b8 requirement 1/8,
   unchanged: it is never replayed); the transcript's existence selects the flag, nothing else changes.
2. Retry once on "already in use". When a `--session-id <id>` call fails and its stderr or stdout matches
   `SESSION_IN_USE_RE` (`Session ID .* is already in use`, case-insensitive), the supervisor marks the session
   started and retries the same message once, in the same turn, with `--resume <id>`; the retry's result is the
   attempt's result. A `--resume` call that fails the same way is not retried again (it is a fault as today). The
   retry is recorded: the attempt row of the turn carries `"retried_resume": true`. Uncertain return codes come
   first: rc 17 and rc 124 never trigger the same-turn resume retry, whatever the captured output says. On the persistent path a
   refused `--session-id` start is followed by one `--resume` start; b8's two start attempts before the per-turn
   fallback are unchanged, and none of them is a `--session-id` start once the id is resumable.
3. The safety valve on founder rule 4. A fault episode (`logs/fault.json`) counts the consecutive faulting turns
   on its step (`count`, `last_at`, `step` = `{acc, model, tier}`). When a step faults and the episode on that
   same step already spans at least `FAULT_ESCALATE_S` (1800 s, from `since` to now) with this fault making
   `count >= FAULT_ESCALATE_COUNT` (3), the fault is escalated: the walk continues from that step exactly as for a
   quota failure (the other account of the tier, then Astra, then Opus 5.5, never below the floor; the usual
   `fallback started`/`fallback moved` bookkeeping persists the winning step), one top-level dev-channel line
   `engine fault escalated: tier <k> <acc> (<model>): <what>` (outbox id `fault-<episode_id>-escalated`, durable in
   `logs/fault.json` as `escalated: true` before it is queued, reconciled at start like the fault line) is posted
   once per episode, and the episode stays open with `probe_after` one `TIER_PROBE_S` (3600 s) from the escalation.
   A fault file written before b14 (an open episode with `episode_id`, `since`, `text`, `queued` but no `count`,
   `last_at` or `step`, the shape of the 2026-10-16 outage) is adopted by the next fault on any step: the episode
   id and `since` are kept, the already-queued line is not queued again, `step` is set from that fault, `count`
   starts at 1 and `last_at` at that fault; the rule then applies as usual (the span counts from the old `since`). Below the threshold nothing changes: a fault still stops the walk and the same engine is retried on
   the back-off (b12 requirement 12). Inside an escalated walk a fault on a later step is recorded and the walk goes
   on (the turn is already the rule-4 exception); it never opens or replaces an episode. Uncertain failures
   (a crash, rc 17, or a timeout, rc 124) retain b8's precedence everywhere: the runner retires the process, the
   current events get their durable disposition, and the walk stops without replay or fallback, inside an
   escalated walk and on a probe alike; the valve's bookkeeping (the count, the escalation and its line, the
   probe) changes eligibility only for a later turn; an uncertain failure on a later step inside an escalated walk
   leaves the open episode untouched. While an escalated
   episode is open and its faulted step is on hold (probe not due), the step that serves is persisted as a move
   (engine file, fallback episode) even when nothing else failed in that turn.
4. The return. While an escalated fault episode is open, the faulted step is tried only when its `probe_after`
   has passed; then the walk starts at the faulted step and continues with the ordinary rotation from the
   effective pair. A success on the faulted step closes the fault episode (`closed_at`) and lets the fallback
   bookkeeping do the rest (the configured pair closes the fallback episode with `fallback ended` and is written
   back to the engine file; another step is a `fallback moved`). A fault on the probe does not stop the walk and
   does not re-escalate: the walk continues at the effective pair, `count` grows, `probe_after` moves one hour out.
   Rule 3's hourly tier probe (`engine-runtime.json` `probe_after`) is unchanged and independent; when both are
   due the faulted step goes first. A served turn on the faulted step, a served turn on the configured pair (the
   fallback episode ends with it), or an operator's explicit `engine` selection closes the fault episode. A second
   step that faults while an escalated episode is open (the fallback step itself develops a fault) replaces the
   episode: the new step's episode starts at count 1 under rule 4, the old probe is dropped and the old step
   rejoins the ordinary rotation; the new episode escalates by the same rule, and its escalated walk reaches the
   old step again.
5. Status and the daily digest name a long fault episode. When `logs/fault.json` holds an open episode whose
   latest fault (`last_at`) is at least 1800 s after its `since` (both read from the file, so the line is the
   same for every reader), `hydra status` prints, immediately after the `engine fallback:` line (when there is no such line,
   immediately after the `identity:` line, where it would be), `fault episode: tier <k> <acc> (<model>) since <PDT time>, <count> faults over <minutes> min` (minutes =
   `last_at` minus `since`, rounded down)
   followed by `, escalated at <PDT time>` when escalated; nothing is printed for a shorter or closed episode. The
   daily digest timer event (`add_timer_event(digest=True)`) carries the same line as a second line of its text,
   so the manager's digest names the episode; README states it in these words: "The daily digest must name
   every open fault episode spanning at least 30 minutes."

6. Nothing else moves. Rule 4 for faults under the threshold, rules 1-3 and 5 of b12, the b11 compaction and
   rollover bookkeeping (verify, thresholds, engine order), the b13 status lines and every other supervisor
   behaviour are unchanged. Nothing below Opus 5.5 ever runs as the manager.
7. Tests the candidate adds in `tests/manager/test_b14_session.py` (fake engines and posters, temporary homes,
   a controlled clock and a short engine timeout; never a real engine, GitHub or Slack): the transcript-exists
   resume on both paths; the same-turn `--resume` retry with the attempt row; a `--resume` failure not retried;
   the escalation after exactly three faults over thirty minutes and not before (two faults over an hour, three
   faults over ten minutes); the escalation walk order and notices; the probe return on the configured and on a
   non-configured step; a faulting probe that keeps the effective pair; the thirty-minute status and digest lines (two faults 35 minutes apart show the line without
   escalating; 29 minutes apart show nothing);
   fixtures replayed from the real rows of both incidents (the sanitized rows in the appendix of this spec, copied
   into the test file; no fixture files are added; the exit requires the file with at least twelve tests whose
   names cover resume, retry, threshold, escalation, probe, status, explicit selection, floor, oct14, oct16); the escalation, the configured return and the explicit
   selection repeated with an explicitly set mode key in the engine file (b8 requirement 7: the mode is kept and
   exactly one `fallback ended` is posted). Every baseline test in `tests/manager` stays byte-identical;
   `loops/b12.acceptance.py` keeps passing unchanged (a single fault still moves nothing).
8. Notes `docs/notes/b14.md`: `## What changed`, `## Evidence` (the measured pytest count, the b12 and b14
   acceptance PASS lines, the exit's last line `[b14] PASS`; before the first exit run the Evidence section says
